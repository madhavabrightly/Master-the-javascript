Async JavaScript & the Event Loop

JavaScript runs one thing at a time — yet it never freezes while waiting for the network. This category explains how that works, why setTimeout(fn, 0) runs after your promises, and how to stop awaiting things in a loop.

10 sections 55+ runnable examples ~85 min read Level: intermediate → advanced

01 — SectionWhy Async Exists

JavaScript runs on a single thread: one call stack, one thing at a time. It cannot do two things simultaneously. Every line you write runs to completion before the next one starts.

That sounds like a limitation — and it is, until you realise what it buys you. Because nothing runs concurrently, you never have two pieces of code touching the same variable at the same instant. No locks, no race conditions, no threads fighting over memory.

★
Brand new to this? Start here

Picture a single barista with one espresso machine. They can only pull one shot at a time. But while the machine is extracting, they don't stand there staring at it — they take the next order, grind beans, hand over a finished cup.

That's async JavaScript. The barista is the call stack. The machine is the operating system doing I/O. Waiting is handed off; working never stops.

Blocking code stops everything

If you wait inside JavaScript, nothing else can happen — because there's only one thread to wait with.

blocking.js javascript 
const start = Date.now();

while (Date.now() - start < 3000) {
  // busy-wait: the call stack never empties, so nothing else can run
}

console.log('Three seconds gone, and the whole program was frozen');
!
Why this matters in a server

A loop like that doesn't just delay your request — it blocks every other request too. One slow synchronous operation can take down an entire Node process. This is the single most common production incident caused by JavaScript.

Non-blocking code hands the waiting off

non-blocking.js javascript 
console.log('start');

setTimeout(() => {
  console.log('timer done');
}, 3000);

console.log('this prints immediately');
terminal output 
start
this prints immediately
timer done

setTimeout doesn't pause anything. It registers the callback with the runtime and returns immediately — so the last line runs first, and the timer's callback runs three seconds later when the stack is free.

  • JavaScript has one call stack — one thing runs at a time.
  • Blocking the stack freezes the entire program, not just the current function.
  • Async APIs hand the waiting to the runtime and hand you back a callback or a promise.

02 — SectionCallbacks

A callback is simply a function you hand to something else, to be called later. It's the original async pattern in JavaScript, and it's still underneath every promise and every await.

Node standardised a convention: the callback takes the error first, then the result. That single rule is why every Node API looks the way it does.

read-config.js javascript 
const fs = require('fs');

fs.readFile('./config.json', 'utf8', (error, content) => {
  if (error) {
    console.error('Could not read config:', error.message);
    return;
  }
  console.log('Config loaded:', content);
});
i
Why error-first?

A callback can only "return" once, and it can't throw to you — by the time it runs, your stack frame is long gone. So the error has to travel as an argument. Checking if (error) first, and return-ing early, keeps the happy path un-indented.

The problem: callback hell

Every async step needs its result before the next one can start. Nest them, and the code marches off the right edge of the screen:

orders.js javascript 
getUser(userId, (error, user) => {
  if (error) return handle(error);

  getOrders(user.id, (error, orders) => {
    if (error) return handle(error);

    getInvoice(orders[0].id, (error, invoice) => {
      if (error) return handle(error);

      sendEmail(user.email, invoice, (error) => {
        if (error) return handle(error);
        console.log('Invoice emailed');
      });
    });
  });
});

Two things went wrong here. The shape is hard to read — but the deeper problem is inversion of control: you handed your continuation to four different functions, and you have to trust each one to call it exactly once, with the right arguments, and never swallow the error.

!
The trust problem

Promises didn't appear because callbacks are ugly. They appeared because a callback gives away control: you cannot know whether it was called twice, never called, or called synchronously before the rest of your function ran.

  • A callback is a function called later, by someone else.
  • Node's convention puts the error first: (error, result).
  • Nesting dependent callbacks produces callback hell and hands away control flow.

03 — SectionPromises

A promise is an object that represents a value you don't have yet. It is a placeholder you can attach behaviour to, pass around, and return — which is exactly what a callback can't do.

States and chaining

A promise is always in one of three states:

  • pending — still waiting
  • fulfilled — finished successfully, with a value
  • rejected — failed, with a reason

A promise settles exactly once. Once fulfilled or rejected, it can never change again. That single guarantee is what makes them trustworthy: you know your continuation runs at most once.

delay.js javascript 
function delay(ms) {
  return new Promise((resolve) => {
    setTimeout(() => resolve(`waited ${ms}ms`), ms);
  });
}

delay(1000).then((message) => {
  console.log(message);   // "waited 1000ms"
});

.then() returns a new promise, which is what makes chaining work. Whatever you return from a then becomes the value the next then receives — and if you return a promise, it's flattened automatically rather than nested.

load-config.js javascript 
readFile('./config.json')
  .then((content) => JSON.parse(content))
  .then((config) => fetch(config.apiUrl))
  .then((response) => response.json())
  .catch((error) => console.error('Something failed:', error.message))
  .finally(() => console.log('Finished, success or failure'));

Compare the shape with the callback version: no nesting, one error handler at the bottom catching anything above it, and the whole thing reads top to bottom.

!
The one mistake everyone makes

Forgetting to return. If you write .then(v => { doThing(v); }) with braces but no return, the next .then gets undefined and your chain silently produces nothing. Either drop the braces or return explicitly.

Combinators — running things together

These four turn a set of promises into a single promise. Choosing the right one is the difference between "wait for everything" and "wait for the first one that works".

MethodResolves whenRejects whenUse it for
Promise.allall fulfillany one rejects (immediately)independent work you need entirely
Promise.allSettledall settle, either wayneverreports where partial failures are fine
Promise.racethe first to settleif that first one rejectstimeouts
Promise.anythe first to fulfillonly if all rejectredundant sources, fastest wins
combinators.js javascript 
// All must succeed — rejects fast if any one fails
const [users, orders] = await Promise.all([getUsers(), getOrders()]);

// Never rejects — inspect each outcome
const results = await Promise.allSettled([getUsers(), getOrders()]);
results.forEach((r) => {
  console.log(r.status, r.status === 'fulfilled' ? r.value : r.reason);
});

// Timeout pattern: whichever settles first wins
const data = await Promise.race([
  fetch('/api/report'),
  delay(5000).then(() => Promise.reject(new Error('Timed out')))
]);
  • A promise is a placeholder for a future value that settles exactly once.
  • then returns a new promise, which is what enables chaining and flattening.
  • Promise.all fails fast; allSettled never fails; race takes the first; any takes the first success.

04 — Sectionasync / await

async and await are syntax on top of promises. Nothing new happens underneath — but the code reads like it's synchronous, which is exactly the point.

  • An async function always returns a promise. Returning 5 returns Promise.resolve(5).
  • await unwraps a promise. It pauses only the current async function — never the thread.
  • Errors become normal exceptions, so try/catch works again.
load-config.js javascript 
async function loadConfig() {
  try {
    const content = await readFile('./config.json');
    return JSON.parse(content);
  } catch (error) {
    console.error('Failed to load config:', error.message);
    return null;          // recovery value, or rethrow
  } finally {
    console.log('loadConfig finished');
  }
}
i
Await doesn't block the thread

People assume await freezes the page. It doesn't. It suspends the function and returns control to the event loop, which keeps running everything else. The function resumes later, exactly where it left off.

Sequential vs parallel — the expensive mistake

This is the single most valuable habit in this category. await in sequence means wait for this, then wait for that. If the operations are independent, you just paid for all of them one after another for no reason.

slow.js — about 3 seconds javascript 
async function loadDashboard() {
  const users = await getUsers();        // 1s
  const orders = await getOrders();      // 1s, starts only after users finishes
  const invoices = await getInvoices();  // 1s, starts only after orders finishes

  return { users, orders, invoices };
}
fast.js — about 1 second javascript 
async function loadDashboard() {
  // Start all three immediately, then await them together
  const [users, orders, invoices] = await Promise.all([
    getUsers(),
    getOrders(),
    getInvoices()
  ]);

  return { users, orders, invoices };
}

Both versions are correct. Only one respects your users' time. The rule: await at the last possible moment, and never inside a loop over independent work.

!
The loop trap

for (const id of ids) { await fetchUser(id); } processes the ids one at a time. If they're independent, use await Promise.all(ids.map(id => fetchUser(id))) instead. Do keep the loop when you genuinely need order, or when you're deliberately rate-limiting.

When you do have an async iterable — a stream, or a paginated API — for await ... of gives you the readable loop and the sequential guarantee:

stream.js javascript 
for await (const chunk of readStream('./big.log')) {
  process.stdout.write(chunk);
}
  • async always returns a promise; await unwraps one.
  • await suspends the function, never the thread.
  • Independent work belongs in Promise.all, not in a sequence of awaits.

05 — SectionThe Event Loop

Everything above only makes sense once you know where the callbacks actually wait. The event loop is the mechanism that decides what runs next.

Four pieces, and only four:

  • Call stack — the function currently running. Single-threaded.
  • Host environment — the browser or Node's C++ layer. Timers and I/O wait out here, off-thread.
  • Task queue (macrotasks) — callbacks from setTimeout, setInterval, I/O, UI events.
  • Microtask queue — promise callbacks, queueMicrotask, MutationObserver.

The whole rule, in one sentence: when the call stack empties, drain the entire microtask queue, and only then take the next macrotask.

i
Why this ordering exists

Microtasks are promise continuations — they must run before the browser paints or handles the next event, otherwise the state your code depends on would be inconsistent. So they get priority, and they get all of it.

Microtasks vs macrotasks, in practice

order.js javascript 
console.log('1 — script start');

setTimeout(() => console.log('5 — setTimeout'), 0);

Promise.resolve().then(() => console.log('3 — promise'));
queueMicrotask(() => console.log('4 — queueMicrotask'));

console.log('2 — script end');
terminal output 
1 — script start
2 — script end
3 — promise
4 — queueMicrotask
5 — setTimeout

The timer was registered first, and it still ran last. Both numbers 3 and 4 are microtasks, so they drain completely before the event loop is allowed to look at the task queue at all.

!
Starvation

Because the microtask queue must be empty before the next macrotask, a promise chain that keeps queueing more microtasks can block timers, rendering and I/O forever. The page appears hung. If you're scheduling a lot of work, prefer setTimeout(fn, 0) or setImmediate to yield between batches.

One more consequence worth knowing: setTimeout(fn, 0) is not "run immediately". It means "run after at least 0ms, once the stack is clear and all microtasks are drained" — and browsers clamp nested timers to 4ms.

  • Synchronous code always finishes first, to the very last line.
  • Then all microtasks drain — promises and queueMicrotask.
  • Then one macrotask runs, and the cycle repeats.
  • Microtasks have priority, which means they can starve everything else.

06 — SectionTimers & Scheduling

There isn't one way to "run this later" — there are six, and they land in different queues. Picking the wrong one is how you get flicker, jank and drift.

!
Timers drift

setInterval(fn, 1000) waits 1000ms, runs fn, then waits another 1000ms. It does not account for how long fn took. If your callback takes 40ms, you drift 40ms further behind every tick — and it never corrects.

drift.js javascript 
// Measure the drift instead of assuming it away
let expected = Date.now() + 1000;

const id = setInterval(() => {
  const drift = Date.now() - expected;
  if (drift > 50) console.log(`setInterval is ${drift}ms behind`);

  expected += 1000;   // the schedule never moves to catch up
}, 1000);

// To correct it, schedule the NEXT tick relative to the target time
function tick() {
  const now = Date.now();
  const delay = 1000 - (now % 1000);   // land on the next whole second
  setTimeout(tick, delay);
}

clearInterval(id);

Debounce — collapse a burst into one call

Every keystroke firing a search request is the classic performance mistake. Debounce waits for quiet; throttle guarantees a steady rate.

debounce.js javascript 
function debounce(fn, delay) {
  let timer;

  return function (...args) {
    clearTimeout(timer);          // cancel the pending call
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

const search = debounce((term) => console.log('searching:', term), 300);

search('j');
search('ja');
search('jav');
// Only "searching: jav" runs — 300ms after the typing stopped.
throttle.js javascript 
function throttle(fn, interval) {
  let last = 0;
  let queued = null;

  return function (...args) {
    const now = Date.now();
    const remaining = interval - (now - last);

    if (remaining <= 0) {
      if (queued) { clearTimeout(queued); queued = null; }
      last = now;
      fn.apply(this, args);
      return;
    }

    // Keep one trailing call so the final event is never lost
    if (!queued) {
      queued = setTimeout(() => {
        last = Date.now();
        queued = null;
        fn.apply(this, args);
      }, remaining);
    }
  };
}

const onScroll = throttle(() => console.log('scroll handler'), 100);
i
Both are just closures

Look at where timer, last and queued live — they're inside the outer function, so they survive between calls but are invisible from outside. That's the entire trick, and it's the same mechanism Category 3 covers in depth.

  • Six scheduling APIs, two queues, and one render step — pick deliberately.
  • setInterval accumulates drift; self-scheduling setTimeout can correct it.
  • Debounce waits for quiet; throttle caps the rate.
  • Anything visual belongs in requestAnimationFrame, never a timer.

07 — SectionConcurrency Control

Promise.all(urls.map(fetch)) looks elegant and will happily open five thousand connections at once. Real systems need limits, retries and timeouts — and all three are a dozen lines each.

!
Unbounded parallelism is a bug

Every fetch holds a socket, a file descriptor and memory. Fire 5000 at once and you'll exhaust the connection pool, get rate-limited or ECONNRESET, and in Node you may hit the file-descriptor limit. The fix is not "await them one at a time" — it's a bounded pool.

map-limit.js javascript 
async function mapLimit(items, limit, worker) {
  const results = new Array(items.length);
  let next = 0;

  // Each runner pulls the next index whenever it becomes free —
  // so no worker sits idle while others still have work.
  async function runner() {
    while (next < items.length) {
      const index = next++;
      results[index] = await worker(items[index], index);
    }
  }

  const runners = Array.from(
    { length: Math.min(limit, items.length) },
    () => runner()
  );

  await Promise.all(runners);
  return results;          // original order, regardless of completion order
}

const pages = await mapLimit(urls, 5, (url) =>
  fetch(url).then((response) => response.text())
);

Retries with exponential backoff

Transient failures — a dropped connection, a 503 — usually succeed on a second attempt. But retrying immediately and in lockstep makes the outage worse.

retry.js javascript 
async function retry(fn, { attempts = 3, base = 300, max = 5000 } = {}) {
  let lastError;

  for (let attempt = 0; attempt < attempts; attempt++) {
    try {
      return await fn(attempt);
    } catch (error) {
      lastError = error;
      if (attempt === attempts - 1) break;

      // Exponential backoff WITH jitter.
      // Without the random part, every client retries at the same instant.
      const delay = Math.min(max, base * 2 ** attempt) + Math.random() * base;
      console.warn(`attempt ${attempt + 1} failed — retrying in ${Math.round(delay)}ms`);
      await new Promise((resolve) => setTimeout(resolve, delay));
    }
  }

  throw lastError;
}

const data = await retry(() => fetchJson('/api/report'));

Timeouts that actually cancel

timeout.js javascript 
async function fetchWithTimeout(url, ms) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), ms);

  try {
    const response = await fetch(url, { signal: controller.signal });
    return await response.json();
  } finally {
    clearTimeout(timer);     // never leave a timer holding a reference
  }
}

// Modern shorthand, same behaviour:
const response = await fetch(url, { signal: AbortSignal.timeout(5000) });

// Race-based timeout (works for anything, not just fetch):
const withDeadline = (promise, ms) => Promise.race([
  promise,
  new Promise((_, reject) =>
    setTimeout(() => reject(new Error(`Timed out after ${ms}ms`)), ms)
  )
]);
i
The race-based version leaks

Promise.race rejects the wrapper but the original promise keeps running, and its timer keeps the process alive. AbortController is better because it genuinely cancels the underlying work. When you must use race, clear the timer in a finally.

Turning callbacks into promises

promisify.js javascript 
// Node ships a helper for the error-first convention
const { promisify } = require('node:util');
const { readFile } = require('node:fs');
const readFileAsync = promisify(readFile);

// By hand — the shape every wrapper follows
function readFileText(path) {
  return new Promise((resolve, reject) => {
    readFile(path, 'utf8', (error, data) => {
      if (error) reject(error);
      else resolve(data);
    });
  });
}

// Node also exposes promise-first APIs directly
const fs = require('node:fs/promises');
await fs.readFile('./config.json', 'utf8');
  • Bound your parallelism — unbounded Promise.all exhausts sockets and memory.
  • Retry with exponential backoff plus jitter, and cap the attempts.
  • AbortController cancels work; Promise.race only stops waiting.
  • Wrap error-first callbacks into promises, or use node:fs/promises directly.

08 — SectionErrors in Async Code

Async errors escape in ways synchronous ones never do — a rejected promise nobody awaited doesn't throw at the call site, it surfaces later as an unhandledRejection. These are the patterns that keep failures visible.

the-silent-bug.js javascript 
async function load() {
  try {
    fetchUser();          // no `await` — the rejection escapes the try block
  } catch (error) {
    console.log('This never runs');
  }
}

// Correct: await it so the rejection happens INSIDE the try
async function loadProperly() {
  try {
    return await fetchUser();
  } catch (error) {
    console.error('Caught:', error.message);
    return null;
  }
}
!
return await is not redundant

Linters often flag return await fn() as unnecessary. Inside a try/catch it is required — dropping the await means the rejection happens after the function has already returned, so your catch never sees it and your finally runs before the work is done.

Preserve the cause, and use real error types

errors.js javascript 
// `cause` keeps the original failure attached
async function loadConfig(path) {
  try {
    return JSON.parse(await readFile(path, 'utf8'));
  } catch (error) {
    throw new Error(`Could not load config from ${path}`, { cause: error });
  }
}

// Custom types let callers branch on WHY it failed
class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = 'ValidationError';
    this.field = field;
  }
}

try {
  await saveUser(input);
} catch (error) {
  if (error instanceof ValidationError) {
    showFieldError(error.field, error.message);      // recoverable
  } else {
    throw error;                                     // unknown — do not swallow it
  }
}

Fail-fast vs collect-everything

all-vs-allsettled.js javascript 
// Promise.all rejects immediately — the successful results are DISCARDED
const [a, b] = await Promise.all([works(), fails()]);   // throws; `a` is lost

// allSettled never rejects, so you keep the good work
const results = await Promise.allSettled([works(), fails()]);

const succeeded = results
  .filter((r) => r.status === 'fulfilled')
  .map((r) => r.value);

const failed = results
  .filter((r) => r.status === 'rejected')
  .map((r) => r.reason);

console.log(`${succeeded.length} ok, ${failed.length} failed`);

Process-level safety nets

A rejected promise that nobody handles will, in modern Node, terminate the process. That default is correct — but you want the failure logged with context first.

safety-net.js javascript 
process.on('unhandledRejection', (reason) => {
  console.error('Unhandled rejection:', reason);
  process.exitCode = 1;      // mark the run as failed, exit gracefully
});

process.on('uncaughtException', (error) => {
  console.error('Uncaught exception:', error);
  // The process state is unknown now — log, flush, and DO NOT continue.
  process.exit(1);
});

// Cleanup that must always run
process.on('SIGINT', async () => {
  await server.close();
  await database.end();
  process.exit(0);
});
i
Always release resources in finally

Timers, locks, database connections, file handles. Anything you acquire before an await must be released even if the await rejects — and finally is the only construct that runs on both paths.

  • An un-awaited call inside try is not caught — await it.
  • Use Error's cause option to keep the original failure.
  • Custom error classes let callers recover from specific failures and rethrow the rest.
  • allSettled when partial success matters; all when it doesn't.

09 — SectionStreams & Async Iteration

Everything so far assumed the data eventually arrives all at once. Streams are for when it doesn't — a 4GB log file, a video upload, a live feed. The data arrives in chunks, over time, and you process each chunk as it lands.

The reason is memory, and it isn't subtle.

memory.js javascript 
const fs = require('node:fs');

// These two do the same job. Only one survives a large file.
//
// readFile: allocates the WHOLE file in memory before you see byte one.
// A 4GB file needs 4GB of RAM — and it may exceed Node's heap limit first.
const content = await fs.promises.readFile('./huge.log', 'utf8');
console.log(content.length);

// createReadStream: a small internal buffer, refilled as you consume it.
// Constant memory whether the file is 4KB or 40GB.
const stream = fs.createReadStream('./huge.log', { encoding: 'utf8' });

let bytes = 0;
stream.on('data', (chunk) => {
  bytes += chunk.length;
});
stream.on('end', () => console.log('total bytes:', bytes));

// 'error' is not optional — without a handler an unhandled stream error
// takes the whole process down.
stream.on('error', (error) => console.error('failed:', error.message));
TypeDirectionExamples

Backpressure — the concept everything else serves

A fast producer and a slow consumer is a memory leak waiting to happen. If you keep reading faster than you can write, the unread data piles up in an internal buffer until you run out of memory.

Backpressure is the stream telling the producer to slow down. It's built into the API: write() returns false when the buffer is full, and you wait for the drain event before writing again.

backpressure.js javascript 
const { once } = require('node:events');

async function writeAll(writable, chunks) {
  for (const chunk of chunks) {
    // write() returns false as soon as the internal buffer passes
    // the highWaterMark. Ignoring that return value is how processes die.
    const ok = writable.write(chunk);

    if (!ok) {
      // Wait for the consumer to catch up before producing more
      await once(writable, 'drain');
    }
  }

  writable.end();
}

// In practice you rarely hand-roll this — pipeline() and for-await
// both respect backpressure for you.

pipeline — not pipe

compress.js javascript 
const fs = require('node:fs');
const { pipeline } = require('node:stream/promises');
const { createGzip } = require('node:zlib');

// pipeline() wires the streams together, propagates the FIRST error
// to every stage, and destroys all of them so nothing leaks.
await pipeline(
  fs.createReadStream('./big.log'),
  createGzip(),
  fs.createWriteStream('./big.log.gz')
);

console.log('compressed');

// The older .pipe() does NOT do that. An error in the middle stage
// is emitted on that stream and the others keep running — the destination
// never closes, the promise never settles, and the file is left half-written.
// fs.createReadStream(a).pipe(gzip).pipe(fs.createWriteStream(b));
!
pipe() does not forward errors

This is the single most common stream bug. With pipe() you must attach an 'error' handler to every stream in the chain, and clean up the rest yourself when one fails. pipeline() exists purely to make that automatic. If you take one thing from this section, take this.

Transform — change data as it flows past

uppercase.js javascript 
const { Transform } = require('node:stream');

const upperCase = new Transform({
  transform(chunk, encoding, callback) {
    // call callback(error, data) — exactly once, always
    callback(null, chunk.toString().toUpperCase());
  }
});

await pipeline(
  fs.createReadStream('./input.txt'),
  upperCase,
  fs.createWriteStream('./output.txt')
);

// A transform can also buffer across chunks — useful for parsing.
// This one emits a record for every complete line it sees.
const lineSplitter = new Transform({
  readableObjectMode: true,
  transform(chunk, encoding, callback) {
    this.buffer = (this.buffer || '') + chunk.toString();

    const lines = this.buffer.split('\n');
    this.buffer = lines.pop();          // keep the incomplete tail

    for (const line of lines) this.push(line);
    callback();
  },
  flush(callback) {
    if (this.buffer) this.push(this.buffer);   // don't lose the last line
    callback();
  }
});

Async iteration — the readable way to consume a stream

for-await.js javascript 
const { createReadStream } = require('node:fs');

// A readable stream is an async iterable — no event handlers needed,
// and if your loop body awaits, backpressure is applied automatically.
let bytes = 0;

for await (const chunk of createReadStream('./big.log', { encoding: 'utf8' })) {
  bytes += chunk.length;
}

console.log('total:', bytes);

// CAUTION: chunk boundaries have nothing to do with lines.
// A chunk can end mid-line, or contain twenty lines. Always buffer.
read-lines.js — an async generator javascript 
const { createReadStream } = require('node:fs');

// async function* — yields values over time, and can await inside
async function* readLines(path) {
  const stream = createReadStream(path, { encoding: 'utf8' });
  let buffer = '';

  for await (const chunk of stream) {
    buffer += chunk;

    const lines = buffer.split('\n');
    buffer = lines.pop();          // the last piece may be incomplete

    for (const line of lines) yield line;
  }

  if (buffer) yield buffer;        // never drop the final unterminated line
}

for await (const line of readLines('./access.log')) {
  if (line.includes(' 500 ')) console.log(line);
}

Streams compose like array methods

Once you have an async generator, you can build map, filter and take for streams that look exactly like their array counterparts — and consume a multi-gigabyte file with the same code shape as a five-element array.

compose.js javascript 
async function* map(source, fn) {
  for await (const item of source) yield fn(item);
}

async function* filter(source, predicate) {
  for await (const item of source) {
    if (predicate(item)) yield item;
  }
}

async function* take(source, count) {
  let seen = 0;
  for await (const item of source) {
    if (seen++ >= count) return;
    yield item;
  }
}

// Read a 10GB log, keep only the errors, and stop after the first ten —
// while touching a few kilobytes of memory in total.
const firstErrors = take(
  filter(readLines('./access.log'), (line) => line.includes(' 500 ')),
  10
);

for await (const line of firstErrors) {
  console.log(line);
}

// Note the laziness: `take` returns after ten items, which throws into
// the generators below it, which ends the for-await over the file —
// so the whole file is never read. That is the point.

Web streams — the same idea, in the browser

web-streams.js javascript 
// fetch() gives you a stream, not a string. response.json() just
// consumes it for you. Reading it yourself lets you show progress.
const response = await fetch('/api/large-report');

// Downloads are not instant — check the declared size when there is one
const total = Number(response.headers.get('content-length')) || 0;

const reader = response.body.getReader();
const decoder = new TextDecoder();
let received = 0;
let text = '';

while (true) {
  const { done, value } = await reader.read();
  if (done) break;

  received += value.length;
  text += decoder.decode(value, { stream: true });   // `stream: true` matters

  if (total) console.log(`${Math.round((received / total) * 100)}%`);
}

// Streaming is also how you render a chat response token by token
// instead of staring at a spinner for four seconds.
  • Streams trade a little code complexity for constant memory usage.
  • Use pipeline(), never pipe() — errors must propagate.
  • Backpressure is write() returning false plus the drain event.
  • Chunk boundaries never align with lines — always buffer the remainder.
  • Async generators turn a stream into something that reads like an array.

10 — SectionReal-Time Communication

Polling, Server-Sent Events and WebSockets all deliver "live" data — and they are not interchangeable. Choosing wrong means either wasted requests or a lot of unnecessary infrastructure.

Polling — start here, honestly

poll.js javascript 
async function refresh() {
  try {
    const response = await fetch('/api/status');
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    render(await response.json());
  } catch (error) {
    console.warn('poll failed, will retry:', error.message);
  }
}

// Self-scheduling rather than setInterval: the next request is only
// queued after this one finishes, so a slow server can't pile up requests.
let stopped = false;

async function loop() {
  while (!stopped) {
    await refresh();
    await new Promise((resolve) => setTimeout(resolve, 5000));
  }
}
loop();

// Always stop when the page goes away, and pause when it's hidden —
// a background tab polling every 5s is pure waste.
document.addEventListener('visibilitychange', () => {
  stopped = document.hidden;
  if (!stopped) loop();
});

Server-Sent Events — a stream you subscribe to

sse.js javascript 
// One-way, over plain HTTP, with reconnection handled for you.
const source = new EventSource('/api/events');

source.onmessage = (event) => {
  console.log('update:', JSON.parse(event.data));
};

// Named events let one connection carry several kinds of message
source.addEventListener('price', (event) => {
  updatePrice(JSON.parse(event.data));
});

source.addEventListener('presence', (event) => {
  updatePresence(JSON.parse(event.data));
});

source.onerror = () => {
  // EventSource reconnects by itself. But it retries FOREVER —
  // including on a 401 or a 404, where retrying will never help.
  if (source.readyState === EventSource.CLOSED) {
    console.error('SSE permanently closed');
  }
};

// Server side, for reference — the format is strict:
//   res.writeHead(200, { 'Content-Type': 'text/event-stream' });
//   res.write(`event: price\ndata: ${JSON.stringify(tick)}\n\n`);
// The blank line is what terminates an event. Miss it and nothing arrives.

// Closing: an open EventSource holds a connection slot. Don't leak it.
window.addEventListener('beforeunload', () => source.close());

SSE is underrated

If data only flows to the browser, SSE is almost always the right answer: it's plain HTTP, it works through proxies, it reconnects automatically, and it needs no extra protocol or server library. Reach for WebSockets when you genuinely need to send messages upstream on the same channel.

WebSockets — bidirectional and persistent

socket.js javascript 
const socket = new WebSocket('wss://example.com/live');   // wss, not ws, in production

socket.addEventListener('open', () => {
  console.log('connected');
  socket.send(JSON.stringify({ type: 'subscribe', channel: 'prices' }));
});

socket.addEventListener('message', (event) => {
  const message = JSON.parse(event.data);

  // ALWAYS switch on a type field. A server that adds a new message type
  // must not crash every client that hasn't been redeployed.
  switch (message.type) {
    case 'price':  updatePrice(message.payload);  break;
    case 'error':  console.error(message.message); break;
    case 'pong':   break;
    default:       console.warn('unknown message type:', message.type);
  }
});

socket.addEventListener('error', () => {
  // 'error' carries almost no information by design (it would leak
  // cross-origin details). Use the 'close' event's code instead.
});

socket.addEventListener('close', (event) => {
  console.log('closed', event.code, event.reason);
});
reconnect.js javascript 
// A WebSocket does NOT reconnect on its own. This wrapper does.
function connect(url, onMessage) {
  let socket;
  let attempt = 0;
  let closedByUs = false;
  let heartbeat = null;
  let lastSeen = Date.now();

  function open() {
    socket = new WebSocket(url);

    socket.addEventListener('open', () => {
      attempt = 0;                     // reset backoff after a good connection
      lastSeen = Date.now();
      console.log('connected');

      // Detect half-open connections: a laptop lid closing, a NAT timeout
      // or dropped wifi will not fire 'close'. Only silence reveals it.
      heartbeat = setInterval(() => {
        if (Date.now() - lastSeen > 45000) {
          console.warn('connection looks dead — forcing a reconnect');
          socket.close();
          return;
        }
        socket.send(JSON.stringify({ type: 'ping' }));
      }, 15000);
    });

    socket.addEventListener('message', (event) => {
      lastSeen = Date.now();
      if (event.data === 'pong') return;
      onMessage(JSON.parse(event.data));
    });

    socket.addEventListener('close', () => {
      clearInterval(heartbeat);

      if (closedByUs) return;

      // 1s, 2s, 4s, 8s… capped at 30s. The jitter matters: without it,
      // every client that dropped together reconnects together and
      // hammers the server in synchronised waves.
      const delay = Math.min(30000, 1000 * 2 ** attempt) + Math.random() * 500;
      attempt++;
      console.warn(`reconnecting in ${Math.round(delay)}ms`);
      setTimeout(open, delay);
    });
  }

  open();

  return {
    send(message) {
      if (socket?.readyState === WebSocket.OPEN) {
        socket.send(JSON.stringify(message));
        return true;
      }
      return false;                    // caller decides whether to queue it
    },
    close() {
      closedByUs = true;
      clearInterval(heartbeat);
      socket?.close();
    }
  };
}
!
WebSockets bypass your HTTP security model

There is no same-origin policy, no CORS preflight, and no Authorization header on the handshake unless you add one. Cookies are sent automatically, which means a hostile page can open a socket to your server using the user's session — cross-site WebSocket hijacking. Validate the Origin header, authenticate the handshake explicitly with a token, and re-authorise on every message rather than trusting the connection for its lifetime.

Queueing messages before the socket is ready

outbox.js javascript 
// A socket takes time to open. Anything sent before that is silently
// dropped — so hold those messages and flush them on connect.
const outbox = [];

function send(socket, message) {
  const text = JSON.stringify(message);

  if (socket.readyState === WebSocket.OPEN) {
    socket.send(text);
    return;
  }

  outbox.push(text);
}

socket.addEventListener('open', () => {
  while (outbox.length) socket.send(outbox.shift());
});

// Cap it, or a long outage becomes an unbounded array — the same
// principle as the bounded history in Category 5.
const MAX_QUEUED = 100;
if (outbox.length < MAX_QUEUED) outbox.push(text);
  • Start with polling; move to SSE when the server pushes; WebSockets when it's interactive.
  • SSE reconnects automatically — WebSockets never do. You must write that wrapper.
  • Add jitter to backoff, or reconnecting clients synchronise into a thundering herd.
  • Half-open connections only reveal themselves through heartbeats.
  • Authenticate and validate the origin — WebSockets ignore CORS.

Async & event loop checkpoint

1. What does marking a function async guarantee?

Correct answer: B. async wraps the return value in a promise. There is still only one thread — async is syntax over promises, not concurrency.

2. Given a script with sync code, a Promise.then, and a setTimeout(…, 0), what is the order?

Correct answer: B. Synchronous code finishes first, then the microtask queue drains completely, and only then does the loop take the next macrotask.

3. You need to fetch 10 independent users. Which is correct and fastest?

Correct answer: B. Promise.all starts every fetch at once and waits for all of them. A is correct but 10× slower. C is a common bug — forEach ignores the returned promises, so nothing is awaited. D resolves after the first one and discards the rest.

What you can do now

You can read any async code and know what runs when. You can convert callbacks to promises, pick the right combinator, spot a serialised await loop from a mile away, and explain why setTimeout(fn, 0) loses to a promise. That's the whole foundation of real-world JavaScript.
