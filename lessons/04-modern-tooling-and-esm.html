Modern Tooling & ES Modules

The module system that replaced require(), how Node resolves packages now, what every field in package.json is for, and the build step that turns all of it into something a browser can load.

8 sections 40+ runnable examples ~60 min read Level: intermediate → advanced

01 — SectionES Module Syntax

ES modules are the official module system of JavaScript, standardised in the language itself rather than invented by Node. They use import and export instead of require and module.exports.

math.js javascript 
// Named exports — as many as you like, names are fixed
export const PI = 3.14159;

export function add(a, b) {
  return a + b;
}

// Default export — exactly one per module, name chosen by the importer
export default function multiply(a, b) {
  return a * b;
}
main.js javascript 
// Default first, then named — order is a convention, not a rule
import multiply, { PI, add } from './math.js';

// Rename on import
import { add as sum } from './math.js';

// Or take the whole namespace
import * as math from './math.js';

console.log(add(2, 3));       // 5
console.log(sum(2, 3));       // 5 — same function, different local name
console.log(math.PI);         // 3.14159
console.log(multiply(2, 3));  // 6
!
Default vs named — the difference that bites

A default export has no name of its own, so the importer picks one: import anything from './math.js' works. Named exports must match exactly — import { pi } from './math.js' is an error because the export is PI. Most teams prefer named exports for exactly this reason: rename detection and autocomplete actually work.

Re-exporting

A barrel file gathers several modules behind one entry point. This is how most packages present a clean public surface.

index.js javascript 
export { add, multiply } from './math.js';
export { default as formatPrice } from './format.js';
export * from './constants.js';

Live bindings, not copies

This is the deepest difference from CommonJS. An imported binding is a live view onto the exporting module, not a snapshot. If the exporter changes the value, importers see the change.

counter.js javascript 
export let count = 0;

export function increment() {
  count += 1;
}
main.js javascript 
import { count, increment } from './counter.js';

console.log(count);   // 0
increment();
console.log(count);   // 1  — NOT a copy. The binding is live.

You can't assign to an imported binding though — the view is read-only from the outside. count = 5 in main.js is a runtime error.

Dynamic import()

Static imports must be at the top level and are resolved before any code runs. When you need to load something conditionally, or on demand, use the function form — it returns a promise.

lazy.js javascript 
async function openEditor() {
  // Only downloaded and evaluated when this line runs
  const { Editor } = await import('./editor.js');
  return new Editor();
}

// Conditional loading
if (user.isAdmin) {
  const admin = await import('./admin-panel.js');
  admin.mount();
}

This is how bundlers split code. Each import() becomes a separate chunk fetched only when needed — which is why your app's first load doesn't include the admin panel.

  • export names are fixed; only default exports can be renamed freely on import.
  • Imported bindings are live views, not copied values.
  • Static imports are hoisted and resolved before any code runs.
  • import() is dynamic, returns a promise, and enables code splitting.

02 — SectionESM vs CommonJS

Both systems solve the same problem, and they coexist in the ecosystem. But they are different in ways that matter — especially when you're debugging why something is undefined.

CommonJSES Modules
Syntaxrequire / module.exportsimport / export
ResolutionAt runtime, when the call executesStatically, before execution
StructureDynamic — paths can be built at runtimeStatic — analysable without running
Tree shakingVery hardBuilt in
Top-level awaitNot allowedSupported
__dirnameAvailableNot defined
Top-level thismodule.exportsundefined
BindingsCopied valuesLive views
Strict modeOpt inAlways on
File extensions.js / .cjs.mjs, or .js with "type": "module"
i
Why "static" matters so much

Because ESM imports must be literal strings at the top of the file, a bundler can build the entire dependency graph without executing anything. That's what makes tree shaking — dropping code you never use — possible. With require(someVariable), the bundler simply cannot know what will load.

Replacing __dirname

In ESM there is no __dirname or __filename. You derive them from import.meta.url, which is a real file:// URL:

paths.js javascript 
import { fileURLToPath } from 'node:url';
import { dirname, join } from 'node:path';

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

console.log(join(__dirname, 'data', 'users.json'));

// Node 20.11+ gives you the directory directly:
// console.log(import.meta.dirname);

Mixing the two systems

interop.js javascript 
// ESM importing a CommonJS package:
// `default` is the whole module.exports object
import express from 'express';
import { readFileSync } from 'node:fs';     // Node's built-ins expose named exports

// Named imports from CJS often work, because Node statically
// detects `exports.foo = ...` patterns — but it is not guaranteed.

// Going the other way, Node 22+ can require() an ES module
// (as long as it has no top-level await):
const esmModule = require('./modern.mjs');
  • CommonJS resolves at runtime; ESM resolves statically before anything runs.
  • ESM always runs in strict mode and gives you top-level await.
  • __dirname doesn't exist in ESM — derive it from import.meta.url.
  • Interop works, but the mismatch between live bindings and copied values is a real source of bugs.

03 — Sectionpackage.json & Module Resolution

Node decides whether a .js file is a module or a script by looking at the nearest package.json. The type field is the switch.

  • "type": "module" — every .js is an ES module
  • "type": "commonjs" (or absent) — every .js is CommonJS
  • .mjs — always ESM, regardless of type
  • .cjs — always CommonJS, regardless of type
package.json json 
{
  "name": "my-app",
  "version": "2.0.0",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.js",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./helpers": "./dist/helpers.js",
    "./package.json": "./package.json"
  },
  "files": ["dist"],
  "engines": { "node": ">=20" }
}

What the entry-point fields mean

FieldRead byPurpose
mainNode (legacy)The original single entry point, still the fallback
moduleBundlersA non-standard hint pointing at the ESM build
exportsNode & bundlersThe modern, authoritative map — and a wall
typesTypeScriptWhere the type declarations live
filesnpmAllow-list of what actually gets published
!
exports is a wall, not a suggestion

The moment a package defines exports, deep imports into its internals stop working. require('my-app/dist/utils/secret.js') fails even though the file exists, unless it's listed. That's deliberate — it lets library authors refactor freely. If you maintain a package and add exports, it's a breaking change.

Conditional keys are checked in the order they appear, so types must come first, and import/require let one package serve both module systems from a single name.

how a bare import resolves text 
import 'my-app'   from /src/app.js

1. Is it a Node built-in?          (node:fs, node:path, …)   -> use it
2. Is it a relative path?          ('./x', '../y')           -> resolve from the file
3. Walk up looking for node_modules/my-app
4. Read my-app/package.json
5. If "exports" exists, use it     -> conditions: import / require / default
6. Otherwise fall back to "main"
7. Not found anywhere             -> ERR_MODULE_NOT_FOUND
  • "type" in the nearest package.json decides how .js is treated.
  • .mjs and .cjs always override type.
  • exports replaces main as the authoritative entry map and blocks deep imports.
  • Condition order matters — types first, then import/require.

04 — Sectionnpm & Dependencies

package.json declares what you want; package-lock.json records exactly what you got. Both matter, for different reasons.

The four dependency types

dependenciesAlways, including in productionCode your app needs at runtime
devDependenciesDevelopment installs onlyBundlers, test runners, linters, type packages
peerDependenciesNot installed — you must provide itPlugins: "I work with React 18, but you bring React"
optionalDependenciesBest effort; install failure is not fatalPlatform-specific native addons

{
  "dependencies": {
    "express": "^4.18.2"
  },
  "devDependencies": {
    "vite": "^5.4.0",
    "vitest": "^2.0.0",
    "typescript": "^5.5.0"
  },
  "peerDependencies": {
    "react": ">=18"
  }
}

Version ranges

RangeMeansAllows
^1.2.3>=1.2.3 <2.0.0minor and patch updates
~1.2.3>=1.2.3 <1.3.0patch updates only
1.2.3exactly that versionnothing
1.x>=1.0.0 <2.0.0any minor or patch
>=1.2.3 <2.0.0explicit rangewhatever you wrote
* or latestanythingeverything — avoid
i
Semver is a promise, not a guarantee

^ trusts the package author to bump the major version when they break something. Most do; some don't. This is exactly why package-lock.json exists — it pins the resolved tree so that 1.2.3 today is the same 1.2.3 on CI tomorrow.

The commands you actually use

terminal shell 
npm install express              # add to dependencies
npm install --save-dev vitest    # add to devDependencies
npm install                      # install per package.json, update the lockfile
npm ci                           # clean install from the lockfile — use this in CI
npm outdated                     # what's behind
npm update                       # move within the allowed ranges
npm audit                        # known vulnerabilities
npm audit fix                    # patch what can be patched automatically
npx cowsay hello                 # run a package binary without installing it
npm run build                    # run a script from "scripts"
!
npm install vs npm ci

npm install may update the lockfile. npm ci deletes node_modules and installs strictly from the lockfile — it never modifies it, and it fails if package.json and the lockfile disagree. That determinism is why CI should always use npm ci.

  • Runtime code goes in dependencies; tooling goes in devDependencies.
  • peerDependencies declares compatibility without bundling a copy.
  • ^ allows minor updates, ~ only patches.
  • Commit the lockfile; use npm ci in CI for reproducible installs.

05 — SectionBundlers, Transpilers & Testing

Browsers understand ES modules natively now — so why does almost every project still have a build step? Because a build step does four jobs that the platform doesn't do for you.

  1. Bundling — hundreds of module requests become a handful of files.
  2. Transpiling — TypeScript, JSX and brand-new syntax become widely supported JavaScript.
  3. Tree shaking — exports nothing imports are removed from the output.
  4. Minifying — names shortened, whitespace stripped, output compressed.

The tools, and what each is for

ToolRoleReach for it when
ViteDev server + bundlerAlmost any new web app — fastest default
esbuildBundler + minifierSpeed is the priority; underlying engine of Vite
RollupLibrary bundlerPublishing a package; best tree shaking
webpackBundlerExisting large projects with deep plugin needs
TypeScriptType checker + transpilerYou want types in the codebase
BabelTranspilerTargeting old browsers, or custom syntax plugins
ESLintLinterFinding bugs and enforcing conventions
PrettierFormatterEnding every formatting argument forever
package.json — scripts json 
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "test": "vitest run",
    "test:watch": "vitest",
    "typecheck": "tsc --noEmit",
    "lint": "eslint .",
    "format": "prettier --write ."
  }
}

tsc --noEmit is worth calling out: it runs the type checker and produces no output files. Your bundler handles the transpiling; this just tells you whether the types are actually correct.

Testing, with no dependencies at all

Node ships a test runner now. For a lot of projects you don't need anything else.

math.test.js javascript 
import test from 'node:test';
import assert from 'node:assert/strict';

import { add } from './math.js';

test('add sums two numbers', () => {
  assert.equal(add(2, 3), 5);
});

test('add handles negatives', () => {
  assert.equal(add(-2, -3), -5);
});
terminal shell 
node --test
# ✔ add sums two numbers (1.2ms)
# ✔ add handles negatives (0.3ms)
# tests 2
# pass 2
# fail 0
i
Source maps

Your browser runs minified, bundled code — which is unreadable and has different line numbers. A source map tells DevTools how to map that back to your original files, so breakpoints and stack traces still point at your code. Ship them if you want production errors to be debuggable.

One last idea worth internalising: the build step is not the language. Everything in Categories 1–3 runs exactly as written in Node, and increasingly in the browser too. Tooling exists to optimise delivery — not to make the code valid.

  • Bundling, transpiling, tree shaking and minifying are the four jobs of a build.
  • Vite is the pragmatic default; esbuild powers it; Rollup is best for libraries.
  • tsc --noEmit type-checks without emitting files.
  • node --test gives you a real test runner with zero dependencies.

06 — SectionTypeScript for JavaScript Developers

TypeScript is JavaScript with a compile-time type checker bolted on. Nothing it adds survives to runtime — every annotation is erased. What you get is mistakes caught before you run anything, and editor autocomplete that actually knows your shapes.

i
Adopt it gradually

You don't rewrite anything. Add checkJs: true to tsconfig.json and TypeScript will type-check your existing .js files using JSDoc comments. Rename files to .ts one at a time. strict: false to begin, then turn on strict once the errors are gone.

basics.ts typescript 
// Annotations on parameters and return values
function add(a: number, b: number): number {
  return a + b;
}

// Interfaces describe object shapes
interface User {
  id: number;
  name: string;
  email?: string;              // optional
  readonly createdAt: Date;    // cannot be reassigned after construction
}

// Type aliases are better for unions and primitives
type Status = 'idle' | 'loading' | 'success' | 'error';
type Id = string | number;

// `unknown` is the safe `any` — you must narrow before using it
function parse(json: string): unknown {
  return JSON.parse(json);
}
!
any disables the checker

One any spreads: everything it touches becomes unchecked, and the errors you were paying for disappear. Use unknown for values you haven't validated yet — it forces you to prove the type before using it. Set noImplicitAny so you can't do it by accident.

Generics — one implementation, many types

generics.ts typescript 
function first<T>(items: T[]): T | undefined {
  return items[0];
}

first([1, 2, 3]);        // number | undefined
first(['a', 'b']);       // string | undefined

// Constrained: K must be a real key of T
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { name: 'Alice', age: 30 };
getProperty(user, 'name');   // string
// getProperty(user, 'nope'); // Error — not a key of user

// Async generic helper
async function fetchJson<T>(url: string): Promise<T> {
  const response = await fetch(url);
  return response.json() as Promise<T>;
}

const user2 = await fetchJson<User>('/api/user/1');

Narrowing — teaching the checker what you know

narrowing.ts typescript 
// typeof / instanceof / in all narrow the type
function format(value: string | number | Date) {
  if (typeof value === 'number') return value.toFixed(2);
  if (value instanceof Date) return value.toISOString();
  return value.trim();
}

// A discriminated union is the most useful pattern in TypeScript —
// the `status` field tells the compiler which shape you have.
type Result =
  | { status: 'ok'; data: string[] }
  | { status: 'error'; message: string }
  | { status: 'loading' };

function render(result: Result): string {
  switch (result.status) {
    case 'ok':
      return result.data.join(', ');       // `data` exists here
    case 'error':
      return `Error: ${result.message}`;   // `message` exists here
    case 'loading':
      return 'Loading…';
  }
}
utility-types.ts typescript 
interface User {
  id: number;
  name: string;
  email: string;
}

type Draft       = Partial<User>;                    // every field optional
type Identity    = Pick<User, 'id' | 'name'>;        // just these two
type WithoutId   = Omit<User, 'id'>;                 // everything but id
type Directory   = Record<string, User>;             // a lookup table
type UserFactory = () => User;
type MadeUser    = ReturnType<UserFactory>;          // User

// Compose them into real function signatures
function createUser(input: Omit<User, 'id'>): User {
  return { id: Date.now(), ...input };
}
function updateUser(id: number, patch: Partial<User>): User {
  return { ...findUser(id), ...patch };
}

    "strict": true,
    "noUncheckedIndexedAccess": true,

OptionWhat it gives you
strictTurns on the whole family — noImplicitAny, strictNullChecks, strictFunctionTypes. The single most valuable flag.
noUncheckedIndexedAccessarr[0] becomes T | undefined, because it genuinely can be missing.

i
Types are erased — verify input at the boundary

A type annotation is a promise you make, not something enforced at runtime. fetchJson<User>(url) will happily hand you a number if the API returns one. Types are compile-time only; validate real external data with a schema library (Zod, Valibot) or a hand-written guard.

  • TypeScript is erased at runtime — it catches errors before you run, nothing more.
  • unknown over any; strict is the flag that matters.
  • Generics make one implementation work across types without losing information.
  • Discriminated unions plus narrowing cover most real-world modelling.

07 — SectionTesting in Depth

A test is not there to prove your code works today. It's there so you can change the code next month and find out immediately when you break something.

Node now ships a test runner, so you need nothing installed to start.

math.test.js javascript 
import test from 'node:test';
import assert from 'node:assert/strict';

import { add } from './math.js';

// Arrange / Act / Assert — three blocks, every time
test('add sums two numbers', () => {
  const a = 2;                    // arrange
  const b = 3;

  const result = add(a, b);       // act

  assert.equal(result, 5);        // assert
});
terminal shell 
node --test
# ✔ add sums two numbers (1.4ms)
# tests 1
# pass 1
# fail 0

Table-driven tests beat copy-paste

table.test.js javascript 
const cases = [
  { input: [2, 3],        expected: 5,   why: 'positive numbers' },
  { input: [-2, -3],      expected: -5,  why: 'negative numbers' },
  { input: [0, 0],        expected: 0,   why: 'zeros' },
  { input: [1.5, 2.25],   expected: 3.75, why: 'decimals' }
];

for (const { input, expected, why } of cases) {
  test(`add handles ${why}`, () => {
    assert.equal(add(...input), expected);
  });
}

// vitest has it.each built in
describe('add', () => {
  it.each([
    [2, 3, 5],
    [-2, -3, -5]
  ])('add(%i, %i) === %i', (a, b, expected) => {
    expect(add(a, b)).toBe(expected);
  });
});

Async, errors and fake timers

retry.test.js javascript 
import { describe, it, expect, vi, beforeEach, afterEach } from 'vitest';
import { retry } from './retry.js';

describe('retry', () => {
  beforeEach(() => vi.useFakeTimers());
  afterEach(() => vi.useRealTimers());

  it('retries a failing call and eventually succeeds', async () => {
    const fn = vi.fn()
      .mockRejectedValueOnce(new Error('network'))
      .mockResolvedValueOnce('ok');

    const promise = retry(fn, { attempts: 3, base: 100 });

    await vi.advanceTimersByTimeAsync(500);   // skip the backoff instantly

    await expect(promise).resolves.toBe('ok');
    expect(fn).toHaveBeenCalledTimes(2);
  });

  it('rejects with the last error once attempts are exhausted', async () => {
    const fn = vi.fn().mockRejectedValue(new Error('down'));
    const promise = retry(fn, { attempts: 2, base: 1 });

    await vi.advanceTimersByTimeAsync(100);

    await expect(promise).rejects.toThrow('down');
    expect(fn).toHaveBeenCalledTimes(2);
  });
});
!
Fake timers and unhandled rejections

With fake timers, a rejected promise can sit unhandled while the microtask queue never advances — Node prints UnhandledPromiseRejection and some runners fail the suite. Attach your assertion (await expect(promise).rejects…) before advancing timers, as above.

i
Test behaviour, not implementation

A test that asserts "this private method was called twice" breaks the moment you refactor, without anything actually being wrong. Test the observable outcome — the return value, the emitted event, the written file. If a refactor breaks a test but the feature still works, that test was measuring the wrong thing.

Worth testingNot worth testing
Boundary values (0, -1, empty, max)That a getter returns a field
Error paths and what's thrownGenerated code or library internals
Pure functions with tricky logicExact console output strings
Regression cases — every bug you fixThat a mock was called (usually)
Public API contractsPrivate implementation details
  • node --test gives you a real runner with zero dependencies.
  • Table-driven tests cover many cases without copy-paste.
  • Fake timers let you test retries and timeouts without waiting.
  • Assert on behaviour, not on how it was implemented.

The four leaks you will actually hit

leaks.js javascript 
// 1. Listeners that are never removed
element.addEventListener('click', handler);
// in your teardown path:
element.removeEventListener('click', handler);

// 2. Timers that never stop — they keep the closure, and the process, alive
const id = setInterval(poll, 1000);
clearInterval(id);

// 3. Caches that grow without bound
const cache = new Map();              // grows forever
// fix: an LRU with a max size, or a WeakMap when the keys are objects

// 4. Closures holding onto something enormous
function attach(bigBuffer) {
  // bigBuffer stays in memory for as long as this function does
  return () => bigBuffer.length;
}

// Detached DOM: a removed node still referenced by JS is not collected.
// In DevTools, take two heap snapshots and diff them — that's how you find it.
i
Logpoints instead of breakpoints

Right-click a line in DevTools and choose Add logpoint. It logs an expression every time that line runs without pausing execution and without editing source. For a loop running ten thousand times, it's the difference between a five-second answer and a five-minute one.

Lock it down with CI

Everything above is worthless if it only runs on your machine. Make the pipeline refuse broken code.

.github/workflows/ci.yml yaml 
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4

          node-version: 20

      - run: npm ci          # reproducible install from the lockfile
      - run: npm run lint
      - run: npm run typecheck
      - run: npm test
      - run: npm run build
.github/workflows/pages.yml — publish this site yaml 
name: Deploy course site

on:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  deploy:
    environment:
      name: github-pages
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

  • Measure with performance.now, console.time and the profiler — never guess.
  • Long tasks over 50ms are what make a UI feel frozen.
  • Leaks come from listeners, timers, unbounded caches and captured closures.
  • CI should run install, lint, typecheck, test and build on every push.

ES modules & tooling checkpoint

1. What is the practical advantage of ESM imports being static?

Correct answer: B. Because specifiers are literal strings, a bundler can analyse the graph without running anything and drop the exports nobody imports. Note D is the opposite — dynamic paths are what CommonJS allows and ESM forbids (without import()).

2. A package sets "type": "module". What happens to its .js files?

Correct answer: A. type changes how the runtime interprets .js. .cjs still means CommonJS and .mjs still means ESM, regardless of the field.

3. What does package-lock.json give you that package.json does not?

Correct answer: B. package.json holds ranges like ^4.18.2; the lockfile records the exact tree that was installed — which is why it belongs in version control and why CI uses npm ci.

What you can do now

You can write ES modules properly, explain why they can be tree-shaken and CommonJS can't, configure exports so a package works for both systems, keep dependencies reproducible with a lockfile, and describe exactly what a build step is doing to your code. That's the whole modern toolchain, without the cargo cult.
