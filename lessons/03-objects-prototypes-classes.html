Objects, Prototypes & Classes

Reference semantics, the prototype chain, what this actually points at, and what class really is underneath. Get these right and most "weird JavaScript" behaviour stops being weird.

8 sections 45+ runnable examples ~65 min read Level: beginner → advanced

01 — SectionPrimitives vs Objects

Almost everything in JavaScript is an object — but not quite everything. There are seven primitive types, and they behave differently in one crucial way.

  • string, number, boolean, null, undefined, symbol, bigint

Everything else is an object — including arrays, functions, dates, regexes and maps. The difference that matters every single day is how they're assigned.

Primitives are copied by value. Objects are copied by reference.

value.js javascript 
let a = 10;
let b = a;      // b gets its own copy of the number
b = 20;

console.log(a, b);   // 10 20 — a is untouched
reference.js javascript 
const original = { name: 'Alice' };
const alias = original;     // both names point at the SAME object

alias.name = 'Bob';

console.log(original.name);            // "Bob" — not a copy!
console.log(original === alias);       // true — literally one object
!
const does not make things immutable

const locks the binding, not the contents. You cannot reassign original = {}, but original.name = 'Bob' is perfectly legal. To actually prevent changes you need Object.freeze(), covered in section 05.

Autoboxing — why primitives have methods

Strings are primitives, so how does 'abc'.toUpperCase() work? JavaScript creates a temporary wrapper object, calls the method on it, and throws it away. The primitive itself never changes — which is why strings are immutable.

autoboxing.js javascript 
const name = 'alice';

console.log(name.toUpperCase());   // "ALICE"
console.log(name);                 // "alice" — unchanged

// What happens internally, roughly:
console.log(new String(name).toUpperCase());

Shallow vs deep copy

Since objects are shared by reference, "copying" one needs care. Spread and Object.assign make a shallow copy: the top level is new, but nested objects are still shared.

shallow.js javascript 
const user = { name: 'Alice', address: { city: 'Berlin' } };
const shallow = { ...user };

shallow.name = 'Carol';            // safe — a new top-level property
shallow.address.city = 'Paris';    // leaks! address is the SAME object

console.log(user.name);                    // "Alice"
console.log(user.address.city);            // "Paris"  <-- shared
deep.js javascript 
const user = { name: 'Alice', address: { city: 'Berlin' } };
const deep = structuredClone(user);

deep.address.city = 'Lisbon';

console.log(user.address.city);    // "Berlin" — completely independent
console.log(deep.address.city);    // "Lisbon"
i
structuredClone vs JSON

The old deep-copy trick JSON.parse(JSON.stringify(obj)) silently destroys Date objects, undefined, functions, Map, Set and NaN. structuredClone is built into every modern runtime and handles all of them — but still can't clone functions or class prototypes.

  • Seven primitives copy by value; everything else copies by reference.
  • const protects the binding, not the object's contents.
  • Spread and Object.assign are shallow — nested objects stay shared.
  • Use structuredClone for a genuine deep copy.

02 — SectionThe Prototype Chain

Every object carries an invisible link to another object, called its prototype. When you read a property that isn't on the object itself, JavaScript follows that link and looks there. If it isn't there either, it follows that object's link, and so on until it hits null.

That's the entire inheritance model. There are no classes underneath — only this chain.

object-create.js javascript 
const animal = {
  breathe() {
    return 'inhale... exhale...';
  }
};

const dog = Object.create(animal);   // dog's prototype IS animal
dog.bark = () => 'woof';

console.log(dog.bark());     // "woof"    — own property
console.log(dog.breathe());  // "inhale... exhale..." — found on the prototype

console.log(Object.getPrototypeOf(dog) === animal);   // true
console.log(Object.getPrototypeOf(animal) === Object.prototype);  // true

Fn.prototype is not the same as [[Prototype]]

This trips up almost everyone. Every function has a .prototype property — but that's not the function's own prototype. It's the object that will become the prototype of instances created with new.

constructor-function.js javascript 
function User(name) {
  this.name = name;
}

// Methods go on the prototype so every instance SHARES one copy
User.prototype.greet = function () {
  return `Hi, I'm ${this.name}`;
};

const alice = new User('Alice');

console.log(alice.greet());                                // "Hi, I'm Alice"
console.log(Object.getPrototypeOf(alice) === User.prototype);  // true
console.log(alice.hasOwnProperty('greet'));                // false — it's inherited

Own properties vs inherited ones

own-vs-inherited.js javascript 
const base = { role: 'user' };
const admin = Object.create(base);
admin.name = 'Alice';

console.log(admin.name);                      // "Alice"  — own
console.log(admin.role);                      // "user"   — inherited

console.log(admin.hasOwnProperty('name'));    // true
console.log(admin.hasOwnProperty('role'));    // false
console.log('role' in admin);                 // true  — `in` walks the chain
console.log(Object.keys(admin));              // ["name"] — only own, enumerable
!
Don't use __proto__

obj.__proto__ still works and you'll see it everywhere, but it's a legacy accessor on Object.prototype — slow, and a genuine security risk when the key comes from user input. Use Object.getPrototypeOf() and Object.setPrototypeOf() instead.

i
Object.create(null) for pure dictionaries

A normal object inherits things like constructor, toString and hasOwnProperty. If you're using an object as a lookup table keyed by user data, Object.create(null) gives you a truly empty object with no inherited keys to collide with.

  • Property lookup walks up the prototype chain and stops at null.
  • Fn.prototype becomes the prototype of instances made with new.
  • hasOwnProperty checks one level; in checks the whole chain.
  • Object.create(null) gives you a dictionary with no inherited baggage.

03 — SectionWhat this Actually Is

this is decided when a function is called, not when it's defined. That one sentence resolves most confusion. The same function can have a different this on every call, depending on how you invoked it.

Four rules, in priority order:

  1. new — a brand new object, created for the call.
  2. Explicit — call, apply or bind decides it.
  3. Implicit — obj.method() makes this the object before the dot.
  4. Default — undefined in strict mode (which modules and classes always are), otherwise the global object.
implicit-and-lost.js javascript 
const button = {
  label: 'Save',
  click() {
    return this.label;
  }
};

console.log(button.click());     // "Save" — implicit: this is button

// Detach the method and the link is gone
const detached = button.click;
console.log(detached());         // undefined — nothing before the dot

// Bind it to keep the link
const fixed = button.click.bind(button);
console.log(fixed());            // "Save"
!
The classic bug

setTimeout(this.update, 100) loses this, because the callback is invoked with no owning object. Same for array.forEach(this.handler) and every event listener. Fix it with .bind(this), an arrow function, or by passing () => this.update().

Arrow functions capture this lexically

An arrow function has no this of its own. It uses whatever this was in the surrounding scope when it was written — and it cannot be changed, not even by call or bind.

arrow-vs-function.js javascript 
const timer = {
  seconds: 0,

  startArrow() {
    setInterval(() => {
      this.seconds++;          // arrow: this is `timer` — works
      console.log(this.seconds);
    }, 1000);
  },

  startFunction() {
    setInterval(function () {
      this.seconds++;          // plain function: this is NOT timer
      console.log(this.seconds);   // NaN
    }, 1000);
  }
};
explicit.js javascript 
function introduce() {
  return `I am ${this.name}`;
}

const alice = { name: 'Alice' };
const bob = { name: 'Bob' };

console.log(introduce.call(alice));    // "I am Alice"
console.log(introduce.apply(bob));     // "I am Bob"

const boundToAlice = introduce.bind(alice);
console.log(boundToAlice());           // "I am Alice" — locked in

// `call` and `apply` differ only in how arguments are passed
function add(a, b) { return this.base + a + b; }
console.log(add.call({ base: 10 }, 1, 2));     // 13 — arguments listed
console.log(add.apply({ base: 10 }, [1, 2]));  // 13 — arguments as an array
  • this is determined at call time by the call site.
  • Priority: new > explicit bind/call/apply > obj.method() > default.
  • Arrow functions inherit this and cannot be rebound.
  • Passing a method as a callback detaches it from its object.

04 — SectionClasses

class is syntax sugar over constructor functions and prototypes. There is no new inheritance mechanism — but the syntax is far harder to misuse, and it always runs in strict mode.

User.js javascript 
class User {
  #password;                    // truly private — not just a naming convention

  constructor(name, password) {
    this.name = name;
    this.#password = password;
  }

  get displayName() {           // getter, used like a property
    return `@${this.name.toLowerCase()}`;
  }

  checkPassword(attempt) {
    return attempt === this.#password;
  }

  static fromObject(obj) {      // lives on the class, not on instances
    return new User(obj.name, obj.password);
  }
}

const alice = new User('Alice', 'hunter2');

console.log(alice.displayName);              // "@alice"
console.log(alice.checkPassword('nope'));    // false
console.log(User.fromObject({ name: 'Bob', password: 'x' }).displayName);  // "@bob"

#password is enforced by the language. Outside the class body, the name doesn't even exist — reading it throws a SyntaxError at parse time, not a runtime undefined. That's a real privacy guarantee the old _underscore convention never gave you.

Methods are shared, not copied

shared-methods.js javascript 
class Counter {
  increment() {
    this.value++;
  }
}

const a = new Counter();
const b = new Counter();

console.log(a.increment === b.increment);   // true — ONE function, on the prototype

// Compare with an arrow property assigned per instance:
class Other {
  increment = () => { this.value++; };
}

const c = new Other();
const d = new Other();
console.log(c.increment === d.increment);   // false — a new closure each time
i
Which should you use?

Prototype methods are shared and memory-efficient — use them by default. Instance arrow properties cost one closure per object, but they're bound to the instance, so they survive being passed as callbacks. Use them for handlers you'll hand off.

Inheritance with extends

animals.js javascript 
class Animal {
  constructor(name) {
    this.name = name;
  }

  speak() {
    return `${this.name} makes a sound`;
  }
}

class Dog extends Animal {
  speak() {
    return `${this.name} barks`;      // override
  }

  speakLoudly() {
    return this.speak().toUpperCase() + '!';   // reuse via this
  }
}

const rex = new Dog('Rex');

console.log(rex.speak());             // "Rex barks"
console.log(rex.speakLoudly());       // "REX BARKS!"
console.log(rex instanceof Dog);      // true
console.log(rex instanceof Animal);   // true — the chain reaches Animal

If the subclass defines a constructor, it must call super(...) before touching this — the parent is what actually creates the object.

super.js javascript 
class Animal {
  constructor(name) {
    this.name = name;
  }
}

class Dog extends Animal {
  constructor(name, breed) {
    super(name);            // must run first
    this.breed = breed;
    console.log(this.breed);   // now `this` exists
  }
}
  • class is sugar over prototypes, but always strict and harder to misuse.
  • Methods live on the prototype and are shared by every instance.
  • #private fields are enforced by the language, not by convention.
  • extends wires the prototype chain; super() creates the object.

05 — SectionDescriptors & Copying

Every property is more than a value. It carries three hidden flags that decide whether it can be changed, listed, or deleted.

FlagDefault (plain object)Controls
writabletruewhether the value can be reassigned
enumerabletruewhether it appears in for...in, Object.keys, spread
configurabletruewhether it can be deleted or redefined
define-property.js javascript 
const user = { name: 'Alice' };

Object.defineProperty(user, 'id', {
  value: 42,
  writable: false,       // cannot be reassigned
  enumerable: false,     // hidden from loops and Object.keys
  configurable: false    // cannot be deleted or redefined
});

user.id = 99;                       // silently ignored (throws in strict mode)

console.log(user.id);               // 42
console.log(Object.keys(user));     // ["name"] — id is not enumerable
console.log(user.hasOwnProperty('id'));  // true — it exists, just hidden

Getters and setters

A getter looks like a property from the outside but runs code on every read. That's how computed values stay in sync without you manually updating them.

getters.js javascript 
const circle = {
  radius: 2,

  get area() {
    return Math.PI * this.radius ** 2;
  },

  set diameter(value) {
    this.radius = value / 2;
  }
};

console.log(circle.area.toFixed(2));   // "12.57"

circle.diameter = 10;                  // uses the setter
console.log(circle.radius);            // 5
console.log(circle.area.toFixed(2));   // "78.54" — recomputed on read

console.log(Object.keys(circle));      // ["radius"] — area is not a stored key

Freezing — and why it's shallow

freeze.js javascript 
const config = Object.freeze({
  apiUrl: 'https://api.example.com',
  retries: 3
});

config.retries = 99;                  // ignored
console.log(config.retries);          // 3 — unchanged
console.log(Object.isFrozen(config)); // true

// But freeze is SHALLOW — nested objects are still mutable
const settings = Object.freeze({ inner: { theme: 'dark' } });
settings.inner.theme = 'light';       // works fine
console.log(settings.inner.theme);    // "light"

// Deep freeze needs a walk
function deepFreeze(obj) {
  Object.values(obj).forEach((value) => {
    if (value && typeof value === 'object') deepFreeze(value);
  });
  return Object.freeze(obj);
}
i
Freeze, seal, preventExtensions

preventExtensions stops new properties being added. seal also stops deletions. freeze also makes existing values non-writable. All three are shallow.

  • Properties carry writable, enumerable and configurable flags.
  • enumerable: false hides a property from loops, Object.keys and spread.
  • Getters compute on read; they are not stored values.
  • Object.freeze is shallow — deep immutability needs a recursive walk.

06 — SectionIterables, Map & Set

Arrays aren't special — they just implement the iteration protocol. Anything that does can be spread, destructured and looped with for...of, including your own objects.

range.js javascript 
// Any object with a [Symbol.iterator] method is iterable
const range = {
  from: 1,
  to: 5,

  [Symbol.iterator]() {
    let current = this.from;
    const last = this.to;

    return {
      next: () => current <= last
        ? { value: current++, done: false }
        : { value: undefined, done: true }
    };
  }
};

console.log([...range]);          // [1, 2, 3, 4, 5]
const [first, second] = range;    // 1 2
for (const n of range) process.stdout.write(n + ' ');
!
for...of vs for...in

They are not interchangeable. for...of iterates values and only works on iterables. for...in iterates keys and walks the prototype chain — on an array it gives you "0", "1" as strings, plus any inherited enumerable property. Use for...of for data; avoid for...in on arrays entirely.

spread-and-destructure.js javascript 
const list = ['a', 'b', 'c'];

const [head, ...tail] = list;     // "a", ["b", "c"]
const copy = [...list];
const chars = [...'hello'];       // ['h', 'e', 'l', 'l', 'o']

// Works because strings, arrays, Maps, Sets, generators and
// Node streams all implement the same protocol.
const entries = [...new Map([['a', 1]])];   // [['a', 1]]

Map — keys that aren't strings

map.js javascript 
const users = new Map();

users.set('alice@example.com', { name: 'Alice' });
users.set(42, 'the answer');
users.set({ id: 1 }, 'an object as a key');   // objects can be keys

console.log(users.size);              // 3 — a property, not a count-up
console.log(users.get(42));           // "the answer"
console.log(users.has('nobody'));     // false

// Iteration is ordered by insertion, and gives you [key, value]
for (const [key, value] of users) {
  console.log(key, value);
}

// Convert both directions
const fromObject = new Map(Object.entries({ a: 1, b: 2 }));
const backToObject = Object.fromEntries(fromObject);

Set — uniqueness for free

set.js javascript 
const tags = new Set(['js', 'node', 'js', 'web']);
console.log(tags.size);          // 3 — duplicates were dropped

// The classic one-liner: dedupe an array
const unique = [...new Set([1, 2, 2, 3, 1])];    // [1, 2, 3]

// Membership is O(1) rather than scanning
console.log(tags.has('node'));   // true

// Set algebra
const a = new Set([1, 2, 3]);
const b = new Set([2, 3, 4]);

const intersection = new Set([...a].filter((x) => b.has(x)));   // {2, 3}
const union = new Set([...a, ...b]);                            // {1, 2, 3, 4}
const difference = new Set([...a].filter((x) => !b.has(x)));    // {1}

WeakMap — data the collector can reclaim

weakmap.js javascript 
const privateData = new WeakMap();

class Account {
  constructor(balance) {
    privateData.set(this, { balance });
  }

  deposit(amount) {
    privateData.get(this).balance += amount;
    return this;
  }

  get balance() {
    return privateData.get(this).balance;
  }
}

const account = new Account(100);
account.deposit(50);
console.log(account.balance);      // 150

// When `account` is garbage collected, its WeakMap entry goes with it.
// A plain Map would hold the instance alive forever — a classic memory leak.
// Keys must be objects, and WeakMap is not iterable by design.
  • The iteration protocol (Symbol.iterator) is what makes spread, destructuring and for...of work.
  • for...of gives values; for...in gives keys and walks the prototype chain.
  • Use Map for non-string keys, guaranteed order and a real size.
  • WeakMap attaches data to an object without preventing collection.

07 — SectionClosures & Private State

A closure is a function bundled with the scope it was created in. Every function has one — you only notice it when the inner function outlives the outer call and the variables are still there.

That one mechanism gives you private state, memoisation, factories and half the utility functions you'll ever write.

counter.js javascript 
function counter() {
  let count = 0;                 // no outside access, ever

  return {
    increment: () => ++count,
    reset: () => (count = 0),
    get value() { return count; }
  };
}

const c = counter();
c.increment();
c.increment();

console.log(c.value);    // 2
console.log(c.count);    // undefined — there is no such property

// Each call creates a brand new scope
const other = counter();
console.log(other.value);   // 0 — completely independent
!
The loop bug everyone meets once

var is function-scoped, so every iteration shares one binding. By the time the timers run, the loop is finished and i is 3. let creates a new binding per iteration, which is why the same code prints 0 1 2.

loop-scope.js javascript 
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log('var:', i), 0);     // 3 3 3
}

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log('let:', i), 0);     // 0 1 2
}

// Before `let`, this was the fix — a function called per iteration
for (var j = 0; j < 3; j++) {
  (function (captured) {
    setTimeout(() => console.log('iife:', captured), 0);
  })(j);
}

Memoise — cache results in a closure

memoize.js javascript 
function memoize(fn) {
  const cache = new Map();          // lives as long as the returned function

  return function (...args) {
    const key = JSON.stringify(args);

    if (cache.has(key)) return cache.get(key);

    const result = fn.apply(this, args);
    cache.set(key, result);
    return result;
  };
}

const slowSquare = memoize((n) => {
  console.log('computing', n);
  return n * n;
});

slowSquare(4);    // "computing 4"
slowSquare(4);    // cached — the log does not repeat
slowSquare(5);    // "computing 5"
once.js javascript 
function once(fn) {
  let called = false;
  let result;

  return function (...args) {
    if (!called) {
      called = true;
      result = fn.apply(this, args);
    }
    return result;      // later calls get the FIRST result, not a re-run
  };
}

const init = once(() => {
  console.log('initialising…');
  return { ready: true };
});

init();     // "initialising…"
init();     // silent — returns the cached object

The module pattern

Before ES modules existed, an immediately-invoked function expression (IIFE) was how you got a private namespace. It's still the clearest way to explain what a closure buys you.

module-pattern.js javascript 
const Store = (() => {
  const items = new Map();          // private: unreachable from outside

  return {
    set(key, value) { items.set(key, value); return this; },
    get(key) { return items.get(key); },
    has(key) { return items.has(key); },
    get size() { return items.size; }
  };
})();

Store.set('theme', 'dark');
console.log(Store.size);     // 1
console.log(Store.items);    // undefined — only the returned surface exists
i
Closures vs #private

Both give real privacy. #private fields are per-instance and checked by the language at parse time; closures are flexible and let you keep data entirely outside the object. Closures cost one scope per instance — which is exactly what makes them good for factories and singletons, and wasteful in a loop creating millions of objects.

  • A closure is a function plus the scope it captured.
  • let creates a per-iteration binding; var does not.
  • Memoise and once are just closures holding a cache.
  • The module pattern is an IIFE returning only the public surface.

08 — SectionComposition Over Inheritance

extends is the tool everyone reaches for first and regrets second. Deep hierarchies couple every subclass to every change in the base — and they force you to model things that don't fit.

the-trap.js javascript 
class Animal {}
class Bird extends Animal { fly() { return 'flapping'; } }

// A penguin is a Bird… but it cannot fly.
// It inherits `fly` anyway, and callers have no way to know.
class Penguin extends Bird {}

const pingu = new Penguin();
console.log(pingu.fly());     // "flapping" — a lie baked into the type

The problem isn't the penguin. It's that "is-a" inheritance forces you to inherit everything at once, including things that don't apply. Composition lets you pick the abilities you actually have.

behaviours.js javascript 
// Small, independent behaviour factories
const canWalk = ({ name }) => ({ walk: () => `${name} walks` });
const canSwim = ({ name }) => ({ swim: () => `${name} swims` });
const canFly  = ({ name }) => ({ fly:  () => `${name} flies` });

function createPenguin(name) {
  const state = { name };
  return { name, ...canWalk(state), ...canSwim(state) };
}

function createDuck(name) {
  const state = { name };
  return { name, ...canWalk(state), ...canSwim(state), ...canFly(state) };
}

const pingu = createPenguin('Pingu');
console.log(pingu.swim());     // "Pingu swims"
console.log(pingu.fly);        // undefined — genuinely has no such ability

// pingu.fly();
// TypeError: pingu.fly is not a function — fail loudly, not silently

Mixins when you do want classes

mixins.js javascript 
// A mixin is a function that takes a class and returns a richer one
const Serializable = (Base) => class extends Base {
  toJSON() {
    return JSON.stringify({ ...this });
  }
};

const Comparable = (Base) => class extends Base {
  equals(other) {
    return JSON.stringify(this) === JSON.stringify(other);
  }
};

class User {
  constructor(name) { this.name = name; }
}

class RichUser extends Serializable(Comparable(User)) {}

const alice = new RichUser('Alice');
console.log(alice.toJSON());                        // {"name":"Alice"}
console.log(alice.equals(new RichUser('Alice')));   // true

Delegation — hold it, don't inherit it

delegation.js javascript 
class ConsoleLogger {
  log(message) {
    console.log(`[log] ${message}`);
  }
}

class ApiClient {
  constructor(logger = new ConsoleLogger()) {
    this.logger = logger;        // composed and swappable
  }

  async get(url) {
    this.logger.log(`GET ${url}`);
    return fetch(url);
  }
}

// In a test, you pass a fake — impossible if Logger were the base class
const silentClient = new ApiClient({ log: () => {} });

The practical rule

If a subclass overrides most of what it inherits, or throws from inherited methods, the hierarchy is wrong. Reach for composition. One level of extends for a genuine is-a relationship is fine — three levels is a design smell.

  • Inheritance forces you to take abilities you don't have.
  • Behaviour factories let objects pick up exactly what they need.
  • Mixins compose classes without deep hierarchies.
  • Delegation (holding a dependency) is what makes code testable.

Objects & prototypes checkpoint

1. const copy = { ...original } — what did you just make?

Correct answer: B. Spread creates a new top-level object, but every nested value is copied by reference. Use structuredClone when you need real isolation.

2. What decides the value of this inside a function?

Correct answer: B. this is resolved at call time from the call site — unless the function is an arrow, which captures the enclosing this lexically.

3. Where do methods declared with the shorthand syntax in a class body live?

Correct answer: B. Class methods go on Class.prototype, so a.method === b.method is true. Instance arrow-function properties are the ones that create a new closure per object.

What you can do now

You know when you're sharing an object and when you've actually copied it, why a missing property resolves up a chain instead of being undefined, what this will be at any call site, and what class is doing underneath. That's the difference between writing JavaScript and fighting it.
