Module Fundamentals & CommonJS

Modules are the first thing you meet in any real Node codebase — and the first thing that confuses people. By the end of this page you'll know exactly what require() does, why the module cache exists, and how to survive a circular dependency.

5 sections 25+ runnable examples ~35 min read Level: beginner → intermediate

01 — SectionWhat Modules Are

Modules are self-contained blocks of code that serve a single purpose and can be reused across your application. They solve three critical problems in JavaScript development.

★
Brand new to this? Start here

Picture a workshop full of drawers. A module is one drawer. Anything you put in it stays put, and the other drawers can't knock it over — even if they hold a tool with the same name. The only things anyone can take out are the items you deliberately stuck a label on.

That single idea — private by default, public by choice — is the entire reason modules exist. Everything below is just the mechanics of how Node makes it work.

1. Code organization. Instead of writing thousands of lines in a single file, modules let you split functionality into logical, manageable pieces. Each module handles one concern — database operations, authentication, file utilities.

2. Encapsulation. Modules create a private scope. Variables and functions defined inside a module don't leak into the global namespace. Only what you explicitly export becomes accessible to other parts of your code.

3. Avoiding global scope pollution. In large applications without modules, every function and variable you create gets added to the global object (window in browsers, global in Node.js). This causes naming conflicts, makes debugging harder, and increases the risk of accidental overwrites.

The problem: everything shares one namespace

file1.js & file2.js javascript 
// file1.js
function calculateSum(a, b) {
  return a + b;
}

// file2.js
function calculateSum(a, b) {
  return (a + b) * 2;  // CONFLICT! Same function name
}

// Both functions exist globally, and the second overwrites the first

The fix: each module owns its own scope

math.js javascript 
function calculateSum(a, b) {
  return a + b;
}

module.exports = {
  calculateSum: calculateSum
};
operations.js javascript 
function calculateSum(a, b) {
  return (a + b) * 2;  // No conflict—this is private to operations.js
}

module.exports = {
  calculateSum: calculateSum
};
main.js javascript 
const math = require('./math.js');
const operations = require('./operations.js');

console.log(math.calculateSum(5, 3));         // 8
console.log(operations.calculateSum(5, 3));   // 16
i
Tip

Both files define calculateSum. Without modules, the second would silently win. With modules, each one is private to its file and only the exported name crosses the boundary.

  • A module is a file that owns its own scope — nothing leaks out unless you export it.
  • Modules keep related code together and unrelated code apart.
  • The global namespace stays clean, so two files can reuse the same function name safely.

02 — SectionCommonJS Syntax

CommonJS is a module system standardized for JavaScript outside the browser, primarily used in Node.js. It uses two key mechanisms to define and consume modules: module.exports to publish, and require() to consume.

module.exports — exporting code

module.exports is an object that defines what a module makes available to the rest of your application. Anything assigned to it becomes publicly accessible.

Example 1 — exporting a single function

greet.js javascript 
function greet(name) {
  return `Hello, ${name}!`;
}

module.exports = greet;
app.js javascript 
const greet = require('./greet.js');

console.log(greet('Alice'));  // "Hello, Alice!"

Example 2 — exporting multiple functions as an object

calculator.js javascript 
function add(a, b) {
  return a + b;
}

function subtract(a, b) {
  return a - b;
}

function multiply(a, b) {
  return a * b;
}

module.exports = {
  add: add,
  subtract: subtract,
  multiply: multiply
};
app.js javascript 
const calc = require('./calculator.js');

console.log(calc.add(10, 5));       // 15
console.log(calc.subtract(10, 5));  // 5
console.log(calc.multiply(10, 5));  // 50

Example 3 — exporting constructor functions (classes)

User.js javascript 
class User {
  constructor(name, email) {
    this.name = name;
    this.email = email;
  }

  getInfo() {
    return `${this.name} (${this.email})`;
  }
}

module.exports = User;
app.js javascript 
const User = require('./User.js');

const user1 = new User('Alice', 'alice@example.com');
console.log(user1.getInfo());  // "Alice (alice@example.com)"

require() — importing code

require() is a function that loads and executes a module file, then returns whatever that module exports. The path can be relative (./file) or absolute (/path/to/file).

Example 1 — requiring a local module

utils.js javascript 
function formatDate(date) {
  return date.toISOString().split('T')[0];
}

module.exports = { formatDate };
app.js javascript 
const { formatDate } = require('./utils.js');

console.log(formatDate(new Date()));  // "2026-09-23"

Example 2 — destructuring imports

CommonJS doesn't have destructuring built in, but you can destructure the returned object right in your require statement.

stringUtils.js javascript 
module.exports = {
  uppercase: (str) => str.toUpperCase(),
  lowercase: (str) => str.toLowerCase(),
  capitalize: (str) => str.charAt(0).toUpperCase() + str.slice(1)
};
app.js javascript 
const { uppercase, capitalize } = require('./stringUtils.js');

console.log(uppercase('hello'));     // "HELLO"
console.log(capitalize('hello'));    // "Hello"
!
Watch out

Destructuring a single-function export breaks. If a module does module.exports = greet, then const { greet } = require('./greet') gives you undefined — because there is no greet property on the exported function. Destructure only when the module exports an object.

  • module.exports is the public surface of a file — reassign it, don't just mutate it, when exporting one thing.
  • require() executes the target file and hands back its exports.
  • Relative paths start with ./ or ../; bare names like 'lodash' are resolved from node_modules.

03 — SectionModule Loading Behaviour

How a module is loaded matters as much as how it's written. Three behaviours explain almost every surprise you'll hit: synchronous loading, caching, and circular dependencies.

Synchronous loading

Node.js loads modules synchronously — the require() call blocks execution until the module is fully loaded and evaluated. This is different from browser-based module systems (ES modules) which can be asynchronous.

logger.js javascript 
console.log('Logger module is being loaded...');

module.exports = {
  log: (message) => console.log(`[LOG] ${message}`)
};
app.js javascript 
console.log('App starting...');
const logger = require('./logger.js');
console.log('App loaded logger module');
logger.log('This is a test message');
terminal output 
App starting...
Logger module is being loaded...
App loaded logger module
[LOG] This is a test message

Notice the logger module's console.log runs immediately when require() is called — it blocks the app's execution flow until the module finishes evaluating.

Module caching

Node.js caches modules after the first require(). Subsequent calls return the cached module instead of re-executing it. This improves performance and guarantees you get the same instance everywhere in your application.

config.js javascript 
console.log('Config module loaded');

module.exports = {
  apiUrl: 'https://api.example.com',
  version: '1.0.0'
};
app.js javascript 
console.log('First require:');
const config1 = require('./config.js');

console.log('Second require:');
const config2 = require('./config.js');

console.log('Are they the same object?', config1 === config2);  // true
terminal output 
First require:
Config module loaded
Second require:
Are they the same object? true

The "Config module loaded" message appears only once because the module is cached. It's the same object every time — which is why a shared config object or a database pool stays consistent across your whole app.

i
Tip — the cache is your friend

Because the module runs exactly once, top-level side effects (opening a connection, reading a config file) happen once no matter how many files require it. But that also means editing a file mid-run changes nothing until you restart the process.

Circular dependencies

A circular dependency occurs when Module A requires Module B, and Module B requires Module A. This can produce incomplete exports if you're not careful.

The problem

moduleA.js javascript 
console.log('moduleA starting');

const moduleB = require('./moduleB.js');

module.exports = {
  name: 'Module A',
  greeting: () => `Hello from A. B says: ${moduleB.name}`
};

console.log('moduleA loaded');
moduleB.js javascript 
console.log('moduleB starting');

const moduleA = require('./moduleA.js');

module.exports = {
  name: 'Module B',
  greeting: () => `Hello from B. A says: ${moduleA.name}`
};

console.log('moduleB loaded');
terminal — node app.js output 
moduleA starting
moduleB starting
moduleA loaded
moduleB loaded
Hello from A. B says: Module B

The circular dependency is resolved because Node.js returns a partially loaded module when it detects the cycle. moduleB receives moduleA's incomplete exports (an empty object at that moment), then finishes loading.

!
The trap

If moduleB accessed moduleA.name at the top level instead of inside a function, it would read undefined — because at that moment moduleA hasn't finished assigning its exports yet. Deferring the access into a function (as above) sidesteps the problem.

The fix — restructure to remove the cycle

The cleanest solution is to break the cycle by extracting the shared concern into a neutral third module that neither depends on.

shared.js javascript 
module.exports = {
  getModuleAName: () => 'Module A',
  getModuleBName: () => 'Module B'
};
moduleA.js javascript 
const shared = require('./shared.js');

module.exports = {
  name: shared.getModuleAName(),
  greeting: () => `Hello from A. B says: ${shared.getModuleBName()}`
};
moduleB.js javascript 
const shared = require('./shared.js');

module.exports = {
  name: shared.getModuleBName(),
  greeting: () => `Hello from B. A says: ${shared.getModuleAName()}`
};
app.js javascript 
const moduleA = require('./moduleA.js');
const moduleB = require('./moduleB.js');

console.log(moduleA.greeting());  // "Hello from A. B says: Module B"
console.log(moduleB.greeting());  // "Hello from B. A says: Module A"
  • require() is synchronous — it blocks until the module is evaluated.
  • A module is evaluated once; every later require returns the cached instance.
  • In a circular dependency you may receive a half-built module — break the cycle with a shared third module.

04 — SectionNode.js Modules Internals

How Node.js implements CommonJS

Node.js wraps every module file in a function scope to prevent global namespace pollution. When you write code in a module file, it is actually running inside an invisible wrapper function.

The module wrapper

Every Node.js module is internally wrapped like this:

the invisible wrapper javascript 
(function (exports, require, module, __filename, __dirname) {
  // Your actual code here
});

This wrapper provides five variables automatically available in every module:

  • exports — an alias for module.exports
  • require — the function that loads other modules
  • module — the object representing the current module
  • __filename — the absolute path of the current file
  • __dirname — the absolute path of the current directory

Understanding the wrapper in practice

debug.js javascript 
console.log('__filename:', __filename);
console.log('__dirname:', __dirname);
console.log('module:', module);

module.exports = { test: true };

When you run node debug.js, Node.js effectively executes this:

what Node actually runs javascript 
(function (exports, require, module, __filename, __dirname) {
  console.log('__filename:', __filename);
  console.log('__dirname:', __dirname);
  console.log('module:', module);

  module.exports = { test: true };
})(module.exports, require, module, '/path/to/debug.js', '/path/to');
!
Going deeper — exports vs module.exports

Look again at those wrapper parameters: exports is just a function argument that starts out pointing at the same object as module.exports. So exports.add = add works — you're mutating the shared object. But exports = add silently does nothing, because you've only repointed the local parameter while module.exports still holds the original object.

Rule of thumb: attach properties to exports, but reassign module.exports when you're exporting a single value.

i
Why this matters

Because your code lives inside a function, top-level var and function declarations are local to the module — not global. It also explains why you can't use return at the top of a file to exit early... except that you actually can, because you are inside a function.

The node_modules folder

node_modules is where Node.js stores installed packages and dependencies. When you run npm install, packages are downloaded here. When you require a package by name (not by path), Node.js searches for it in node_modules.

How Node.js resolves module paths

When you write require('lodash'), Node.js follows this order:

  1. Check whether it's a built-in module (fs, path, events, http, and friends)
  2. Look in node_modules in the current directory
  3. Look in node_modules in the parent directory
  4. Continue up the directory tree until reaching the filesystem root
  5. If still not found, throw an error

Here's how that looks on disk:

project structure text 
project/
├── node_modules/
│   ├── lodash/
│   │   ├── index.js
│   │   └── package.json
│   └── express/
│       ├── index.js
│       └── package.json
├── src/
│   ├── app.js
│   └── utils.js
└── package.json
src/app.js javascript 
const lodash = require('lodash');        // Searches node_modules
const utils = require('./utils.js');     // Relative path
const path = require('path');            // Built-in module
i
Tip — the upward walk

That upward search is why a package installed at the project root is usable from any nested folder. It's also why a stray node_modules higher up your filesystem can shadow a local install with an old version.

package.json — the project manifest

package.json is a JSON file that describes your Node.js project, including its dependencies, scripts, metadata, and configuration.

A minimal package.json

package.json json 
{
  "name": "my-app",
  "version": "1.0.0",
  "description": "A simple Node.js application",
  "main": "index.js",
  "scripts": {
    "start": "node index.js",
    "test": "jest"
  },
  "keywords": ["app", "node"],
  "author": "Your Name",
  "license": "MIT",
  "dependencies": {
    "express": "^4.18.2",
    "lodash": "^4.17.21"
  },
  "devDependencies": {
    "jest": "^29.7.0"
  }
}

Key fields explained

FieldPurposeExample
nameThe package name"my-app"
versionSemantic versioning (major.minor.patch)"1.0.0"
descriptionWhat the project does"A simple Node.js application"

Version specifiers

  • ^4.18.2 — allows updates to minor and patch versions (4.x.x where x >= 18)
  • ~4.18.2 — allows only patch version updates (4.18.x)
  • 4.18.2 — exact version, no updates
  • * — any version
  • Your file is wrapped in a function with five injected variables — that's the whole trick.
  • Bare imports walk up the directory tree looking for node_modules.
  • package.json records the entry point, scripts, and dependency ranges for your project.

05 — SectionBuilt-in Modules

Node.js ships with several built-in modules (also called core modules) that you can require without installing anything. Here are the four you'll reach for most often.

File system — fs

The fs module provides functions to read, write, and manipulate files on the filesystem. Most operations come in a blocking (sync) flavour and a non-blocking (callback, or promise) flavour.

Example 1 — reading a file (synchronous)

read-file-sync.js javascript 
const fs = require('fs');

const content = fs.readFileSync('./data.txt', 'utf8');
console.log('File content:', content);
console.log('This line waits for the file to be read');

Use cases: small configuration files, initial data loading at startup.

!
Drawback — it blocks

readFileSync blocks the entire application while reading. In a server that means every other request waits behind it. Reach for the async form on any request-handling path.

Example 2 — reading a file (asynchronous with callback)

read-file-async.js javascript 
const fs = require('fs');

fs.readFile('./data.txt', 'utf8', (error, content) => {
  if (error) {
    console.error('Error reading file:', error.message);
    return;
  }
  console.log('File content:', content);
});

console.log('This line executes immediately without waiting');

Benefit: doesn't block — the rest of your program keeps running while the file is read.

Example 3 — writing to a file

write-file.js javascript 
const fs = require('fs');

const data = 'Hello, this is file content!\nLine 2\nLine 3';

fs.writeFile('./output.txt', data, 'utf8', (error) => {
  if (error) {
    console.error('Error writing file:', error.message);
    return;
  }
  console.log('File written successfully');
});

Example 4 — appending to a file

append-file.js javascript 
const fs = require('fs');

fs.appendFile('./log.txt', 'New log entry\n', 'utf8', (error) => {
  if (error) throw error;
  console.log('Data appended to log.txt');
});

Example 5 — listing directory contents

list-files.js javascript 
const fs = require('fs');

fs.readdir('./', (error, files) => {
  if (error) {
    console.error('Error reading directory:', error.message);
    return;
  }
  console.log('Files in current directory:');
  files.forEach(file => console.log(`  - ${file}`));
});

Example 6 — checking file stats (size, creation time, etc.)

file-stats.js javascript 
const fs = require('fs');

fs.stat('./data.txt', (error, stats) => {
  if (error) {
    console.error('Error:', error.message);
    return;
  }
  console.log('File size:', stats.size, 'bytes');
  console.log('Created:', stats.birthtime);
  console.log('Modified:', stats.mtime);
  console.log('Is directory?', stats.isDirectory());
  console.log('Is file?', stats.isFile());
});

Path utilities — path

The path module provides utilities for working with file and directory paths across different operating systems. Windows uses backslashes, POSIX systems use forward slashes — path hides that difference from you.

Example 1 — joining paths

path-join.js javascript 
const path = require('path');

const fullPath = path.join(__dirname, 'data', 'users.json');
console.log('Full path:', fullPath);
// On Windows: C:\projects\myapp\data\users.json
// On Linux:   /projects/myapp/data/users.json
i
Tip — never concatenate paths by hand

Writing __dirname + '/data/' + file breaks on Windows and chokes on duplicate or missing separators. path.join() inserts the correct separator for the current platform and normalises the result.

Example 2 — resolving to an absolute path

path-resolve.js javascript 
const path = require('path');

// resolve() builds an absolute path and walks .. segments for you
console.log(path.resolve('src', '..', 'config', 'app.json'));
// On Linux: /current/working/dir/config/app.json

// join() only glues segments together; it stays relative
console.log(path.join('src', '..', 'config', 'app.json'));
// config/app.json

Example 3 — pulling a path apart

path-parts.js javascript 
const path = require('path');

const file = '/users/alice/docs/report.final.pdf';

console.log(path.basename(file));  // "report.final.pdf"
console.log(path.dirname(file));   // "/users/alice/docs"
console.log(path.extname(file));   // ".pdf"

// basename with a second argument strips that suffix
console.log(path.basename(file, '.pdf'));  // "report.final"

Example 4 — parsing into an object

path-parse.js javascript 
const path = require('path');

const parsed = path.parse('/users/alice/report.pdf');

console.log(parsed);
// {
//   root: '/',
//   dir: '/users/alice',
//   base: 'report.pdf',
//   ext: '.pdf',
//   name: 'report'
// }

// format() is the inverse of parse()
console.log(path.format({ dir: '/users/alice', name: 'summary', ext: '.md' }));
// "/users/alice/summary.md"

Example 5 — normalising messy paths

path-normalize.js javascript 
const path = require('path');

console.log(path.normalize('/users//alice/./docs/../report.pdf'));
// "/users/alice/report.pdf"

// Useful for turning a filesystem path into a URL path
console.log('/static/' + path.relative('/users/alice', '/users/alice/img/logo.png'));
// "/static/img/logo.png"

Also worth knowing — http and events

Two more built-ins show up constantly in real Node code. They also demonstrate why modules matter: both are loaded with a bare require() and neither needs installing.

http — a server in ten lines

server.js javascript 
const http = require('http');

const server = http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'text/plain' });
  res.end('Hello from a built-in module\n');
});

server.listen(3000, () => {
  console.log('Server running at http://localhost:3000');
});

events — the EventEmitter pattern

events.js javascript 
const EventEmitter = require('events');

const emitter = new EventEmitter();

emitter.on('greet', (name) => {
  console.log(`Hello, ${name}!`);
});

emitter.emit('greet', 'Alice');  // "Hello, Alice!"
  • fs covers files and directories — prefer the async form on hot paths.
  • path makes your path handling work on every operating system.
  • http and events are the foundation the rest of the Node ecosystem is built on.

Module & CommonJS checkpoint

1. You require the same module twice in one process. What happens the second time?

Correct answer: B. Node caches the module after the first require, so you get the exact same object back — which is why shared config and connection pools stay consistent.

2. Which variables does the Node module wrapper inject into every file?

Correct answer: C. Those five are the parameters of the invisible wrapper function. __dirname and __filename are absolute paths on the current machine.

3. Module A requires B, and B requires A. What does B receive for A?

Correct answer: B. Node hands back the in-progress exports to break the deadlock. Access them lazily (inside a function) to avoid reading undefined.

What you can do now

You can split a program into modules, export exactly what you mean to, explain why require() blocks, predict what the cache will do, and untangle a circular dependency instead of praying. That's the foundation every Node codebase sits on.
